**L-1 · BLOCKER · No stage is given the duty to *write* a terminal `subtree: complete`. Every leaf-terminated subtree therefore trips the dead-child rule and escalates. The simplest possible tree does not survive.**
The plan defines the schema (`2-plan.md:42-49`), the single writer (`:48`), and a write duty for the **failure** path only (`:68` — a blocked node writes `subtree: incomplete` + `escalation:`). No text and no criterion assigns the **success**-path write. `1.5-criteria.md:57-61` (S-F1.4) requires the schema, the referencing sites, and the single-writer rule — not a write duty. Stage 6 step 2 (`stage-6:13-14`) ends a leaf with "planning of this node is done"; a leaf never reaches stage 6.5, so nothing in the loop ever tells it to write a terminal status.

*Trace (root + one leaf child A — the smallest decomposing tree):*
1. A: stages 1→5, gated clean. Stage 6 → LEAF → "planning of this node is done". A's owner returns.
2. Root at stage 6.5 polls `tree/A/_status.md` for a terminal `subtree:`. A's status has `gate: clean` and (at best) `subtree: incomplete` — nobody wrote `complete`.
3. D3 fires literally: "A child whose owner **returned without writing a terminal `_status.md` is DEAD, not done**" (`2-plan.md:62-63`). A is declared dead.
4. Re-dispatched once. The resumed A finds `plan.md` + 6 records present and hash-current ⇒ every stage-done predicate satisfied ⇒ stage 6 → LEAF → returns. Still no terminal status.
5. "A dead child is re-dispatched once, **then escalated**" (`:64-65`) ⇒ escalation ⇒ under RAT3, HALT + relay to a sleeping owner. **The run stops on a perfectly clean two-node tree.**

X1 cannot catch this: both its arms (`1.5-criteria.md:438`) hand the agent fixtures whose statuses are *pre-written* ("all children terminal"), so the fixture supplies exactly the artifact whose production is unassigned.
*Instead:* assign the write explicitly and per-altitude — stage 5 writes `gate:` + `plan_sha256`; **stage 6's LEAF branch writes `subtree: complete`** (a childless node is vacuously subtree-complete); stage 6.5 writes it for decomposing nodes after the join clears — and add a positive per-site assertion for each of those three writes.

**L-2 · BLOCKER · Escalation (D4) and death (D3) are the same observable event, so the escalation channel — the thing F1 says is missing — defeats the join at every altitude.**
D3's dead test is "the owner **returned** without writing a **terminal** `_status.md`" (`2-plan.md:62-63`). D4's escalating node writes `subtree: incomplete` (non-terminal), `gate: blocked-<severity>`, `escalation: <question>` and **returns** (`:68-72`). An escalating child therefore satisfies the dead predicate exactly. No rule orders the two.

*Trace (root → B → C, C a leaf):* C's stage-5 gate produces a blocker on a seam question. C writes `escalation:` and returns. B's join sees a non-terminal status with an `escalation:` key. Which rule fires?
- If **D3**: B re-dispatches C (burning the one re-dispatch and re-deriving the same blocker with fresh agents that may now answer it differently), then escalates.
- If **D4**: B must "resolve it within its own scope or relay it verbatim upward" (`:69-72`). To relay, B returns to root — with its own `subtree: incomplete`, because B's subtree is not complete. **Root now applies D3 to B and declares B dead**, re-dispatching a node that was correctly escalating.

Either branch mis-decides, and the second one recurses: *escalation is indistinguishable from death at every level*, so the fix for F1's "RAT3 travels over a channel no stage defines" defines a channel that the join itself destroys. No criterion tests the disambiguation: S-F1.3 asserts the dead rule and S-F1.5 asserts the escalation route (`1.5-criteria.md:54-63`) as independent sentences, and X1's holed fixture is the *no-status-at-all* case only.
*Instead:* add a fourth `subtree:` value or a terminal-with-escalation state (`subtree: escalated`, terminal) so the join can distinguish "returned mid-work" from "returned with a question", and state the precedence explicitly: an `escalation:`-bearing status is **never** dead.

**L-3 · BLOCKER · SEAM's reopen detector is not computable as specified: there is no schema slot for the per-child expected `seam_rev`, and no rule says when `seam_rev` increments.**
D5 (`2-plan.md:75-79`): "each node records, **per child**, the `seam_rev` it planned against. When a child's `_status.md` reports a **higher** `seam_rev`, the parent's seam review reopens." Two halves are missing:

So the comparison has no left-hand operand on disk. A parent cannot compute "higher than what I planned against".
2. **What increments `seam_rev`?** No text. Both readings break:

BIND then un-runs 6 records at every ancestor. A single typo fix at depth 4 costs 24 fresh cold agents and (see L-6) potentially a new top-split approval.

By the plan's own routing table, a Tier-1 fix that is "un-checkable" is a **blocker** (`2-plan.md:260`), and F2 is Tier-1 (`1-spec.md:92`). S-F2.2 only asserts the reopen *sentence* exists (`1.5-criteria.md:80-83`); X4 tests the *assembly-time* contradiction check, never the reopen trigger.
*Instead:* make `children:` a structured map (`children: {child-a: {seam_rev: 3, subtree: complete}, …}`) so the expectation is on disk; and define the increment mechanically — `seam_rev = <a short hash of the node's normalized §3 seam slice>`, so "did the seam change" is a diff, not a judgment (and monotone-comparison becomes equality-comparison, which is what the rule actually needs).

**L-4 · MAJOR · KIL's "`plan_sha256` post-dates the kill" is not a disk predicate, contradicting D2's own claim two lines later — and the only timestamp in the schema makes it trivially true.**
