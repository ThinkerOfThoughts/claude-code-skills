# Cascade levels — planning top-down, one level at a time

A level is a tier of the decision pyramid. Start where the top sits (for example an interface the lower pieces plug into) and go down. Record the level order in the ledger as a direction line and have the owner confirm the sentence (router rule 2) before level 1; only the picture check (`stages/cascade-method.md` "The picture check") and this question precede a batch. Work one level at a time through steps a to e. The definitions (derived lines, gap rule, trio, compliance, pile-up) are in `stages/cascade-method.md`.

**a. Draft.** Write the level's design lines as derived lines. Every line cites the rule, default, ruling or owner line it derives from, with H or M. Apply stage-4's "New parts name their alternatives" rule to every line. A line that prescribes how code or data is handled starts from the existing mechanism that does the job, whole or with the smallest change, or says none exists (`stages/cascade-method.md` "Facts"). A level draft is held to the same line as a build answer (`stages/cascade-build.md`, step 2). List the items you cannot derive and the ones that are non-obvious. Where the owner may be needed, write `batch candidate: <condition>` (the gap condition or always-to-owner entry), never "ask the owner" or "open for the owner". Word each item you hand back as the exact text the owner will see: a `batch candidate: <condition>` line is rewritten as owner-ready text when it is handed back (its gap condition is still named at assembly, step e), because the checks below read that text; before wording an item, look it up against the owner's rulings and the principles (`stages/cascade-method.md` SR1).
**b. Trio.** Run the trio for each non-obvious item. Its answer becomes a derived line. A trio FLAG `owner` or `NO RULE DECIDES` is an item handed back: word it as step a says.
**c. Compliance check.** Run the compliance check (`stages/cascade-method.md` "Compliance") on every line of the level. A rule a line cites records where it came from and passes nothing. A line counts as `stages/review-order.md` says ("What a full review returns", "Fix checks"), and only with a valid provenance tag. Execute the routes it proposes (fix, trio, owner; correct, tag or re-cite for the origin record). Items the check routes to the owner (route owner) are worded right after it, as step a says. Then assemble the candidate batch as text in the layout of step e (the gap items, the review list, the H lines, any wrapper sentence). When the draft check is done and the batch is assembled, spawn a second `stages/role-compliance-check.md` agent on the assembled batch text (the batch check; it and step d's red-team review the batch), to test it as step d's four tests say; it is a new agent, because the batch text did not exist when the first check ran. A change to a line that appears in the batch changes the batch text, so the batch is re-assembled.
**d. Red-team.** Spawn one `stages/role-gap-redteam.md` agent (foreground). It gets the level draft with the candidate batch as one artifact, the guarded-change files named in `cascade.redteam` (the charter in full; of the stage-3 file, the "Stage-3 additions" on the coverage challenge, the ratification audits and the five-lens output shape; the criteria-label audits do not apply), and `stages/cascade-method.md`. Its other inputs are what `stages/review-order.md` ("What a reviewer reads") gives for a level draft (for a build answer, what it gives for a build answer), and the routes of its findings are as that file says; a finding that is a gap moves to the batch, and a builder note does not (`stages/review-order.md`, "Builder notes").
**d, on the batch text.** The red-team's "candidate batch" is the batch text assembled in step c. Put the four tests below in the prompt of the batch check and of the red-team, and tell the red-team that its review counts only findings on the batch text (the text the owner will read), while findings on draft lines that do not appear in the batch are reported separately in its body and fixed in the lines as steps c and d do today. Its batch audit also tests the batch text, and a failure of any of them is a finding:
1. every claim is factually right (a claim about the system needs a facts file);
2. no question is too broad, too narrow, or already decided by a rule or an owner line;
3. nothing is credited to the owner unless an OWNER or CONFIRMED line or an owner statement backs it, and a derived line is never called the owner's;
4. each question carries its own data.
A line that appears in the batch (an H line, a review-list line, a gap item) is batch text: a finding on it is fixed in the draft line and in the batch text. A gap the red-team moves into the batch is worded.
**e. Owner batch.** Post one batch for the level, as pasted chat text in a turn with no question call, and only after the review of "Review and post" below. **Hard gate:** a gap item (section 1) is posted only if you name, at assembly time, its gap condition or its always-to-owner entry, with a one-line reason it needs the owner (for an always-to-owner entry, that it changes the owner's decision; for condition (2), that the conflict survived the mechanism test). Anything added to the draft or the batch after the red-team's batch audit (by a later edit, a judge, or the planner) is tested the same way when it is added. An item that cannot name one is recorded as a derived line, as the gap rule says, not posted. Layout, in this order:
1. **Gap items.** For each: the question, which gap condition or always-to-owner entry applies with the one-line reason, options as full sentences with the current default marked, and "none of these".
2. **Review list.** The line, the rule it cites, its confidence and, for trio lines, the vote. Members: every M line, every line whose tag or cited rule the check changed, every derived line that differs from earlier approved text (an equivalent rewrite excepted), every direction line (as a full read-back sentence), every build-time M line not yet reviewed.
3. **H lines**, verbatim, grouped by the rule they cite, for objection only.
Group sections 1 and 2 by detail: **design** (changes what the thing does for its user or what other work depends on), **mechanism** (how it is done inside), **wording** (strings, names, comments). Number the items so the owner can answer by number. An unanswered item was missed: re-surface it. Track the gap items in the Cascade block under Owner batches; the Owner questions list stays the owner's own questions.

**Review and post.** The batch text gets one full review and fix checks, no second review (`stages/review-order.md`, "Text put to the owner"); its reviewers are the batch check of step c and the red-team of step d. It is not copied into a record file and not stamped: the gate tool (`stages/cascade-build.md` "Gate record format") is used only for build answers. Fix the findings as the review order says, then post the batch text verbatim, as pasted chat text, in the layout of step e.

Re-posting an unchanged batch needs no new check unless a Decisions, Owner statements or Approvals line of the ledger changed since it was checked; a part cut from a posted batch is new text and is checked.

**After the batch.** Answers become rules (`stages/cascade-method.md` "Owner answers become rules"); lines they change go back through step c. Record `batch <level> — <ts> "quote"` under Approvals when every gap item is answered and the review list reviewed. A line that changes after its level's batch was approved goes on the next batch's review list (or the build batch), and `sheet_version` is bumped as in the base stages. Stage 4 (the spec) starts once every level's batch is approved. Draft the next level once the gap items are answered; the review list can be answered later but must be done before hand-off, which needs every level's batch approved.
