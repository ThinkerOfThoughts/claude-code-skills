# Example design invariants: Companion-Emergence

> These are the real design invariants of the Companion-Emergence project, privacy-filtered (people's names
> replaced with "the owner" or "a collaborator", private notes removed) and otherwise left as they are,
> project specifics included. They show what a working invariants doc looks like after a few weeks of use:
> one checkable sentence per row, the owner's own words and a date in the second column, amendments dated
> in place. Use them as a starter to adapt, not as rules to adopt.

status: REVIEWED 2026-09-15; I4 AMENDED 2026-09-28 and 2026-09-29, I8 AMENDED 2026-09-29 and 2026-10-22 (the owner)

Standing architectural rules the owner has set. Every plan-ledger sheet, spec, red-team and drift check is checked
against these, row by row. A line is added only with the owner's words and a date; a line is removed only by the owner.
Seeded 2026-09-15 from quoted rulings in earlier planning transcripts; reviewed by the owner the same day.

| # | Invariant (one checkable sentence) | Why (the owner's words, date, source) |
|---|---|---|
| I1 | There is one memories database; hebbian associations live in `memories.db`, not a separate file. | "the hebbian db needed to be merged into the main memory db as having them separate is fragile (On one occasion a persona needed to have several of her hebbian db links reconstructed after being copied from one VM to another)" — 2026-09-15; #128; P4 Stage 1. |
| I2 | A per-memory attribute (embedding, cluster tag, the memory's own emotion tag) is stored on the memory row, or in a memories-side table keyed by memory id; never in a content-addressed side file. Emotion SIGNAL entries (standalone rows holding only the emotional state at time of entry, with no memory content) are not per-memory attributes; they are a separate thing, see I8. | "The per-memory embeddings were supposed to be stored as an additional column in the memory db" — 2026-09-13; #259. |
| I3 | Behaviour thresholds (floors, gaps, cutoffs) are derived or self-calibrating; a hardcoded empirical constant is a tracked defect, never a finished answer. | "magic numbers in code are very rarely the right answer" — 2026-09-12 14:20; "is there a way that can happen automatically? … recalibrates the floor/gap size for the memory db as it is currently" — 2026-09-09 16:40; #250. |
| I4 | On automatic (passive, per-turn) recall, semantic retrieval runs first and ranks first; the lexical/importance/hebbian/recency results are always merged in below the semantic ones, and when the same memory is found by both, the semantic result is the one kept (dedup favors semantic). Exception: monologue-family memories that were not reranked (gated only by the cosine pass mark) rank below keyword genuine hits. On a kindled-initiated search, semantic is the default mode and the kindled can switch it to lexical. | "The semantic search is supposed to be the primary mechanism, the existing lexical is the fallback" — 2026-09-09 20:21; "it runs first on automatic recall, its the default option for Kindled initiated searches but can be switched for lexical" — 2026-09-15; AMENDED 2026-09-28 (name-recall fix): lexical always merged in ("Always, merged in") and "Do it this way: deduping favors the semantic"; AMENDED 2026-09-29 (name-recall F13): non-reranked monologue below keyword genuine, the owner: "Only the tail drops" + "Yes, that's right" to the read-back order + "option 1" to this exception wording. |
| I5 | A memory opened in full gets the full recall bump and is enqueued for reappraisal, regardless of which path surfaced it. | "if it surfaces it gets the full +1 to its recall score. Doesn't matter *how* it got surfaced" — 2026-09-10 17:01; "If a memory gets opened, it doesn't matter how it surfaced … Yes it goes back into the reappraisal queue!" — 2026-09-10 18:30. |
| I6 | Bulk background work (backfills, sweeps) stays off the message hot path; a single bounded per-turn step is acceptable; the lag rule targets floods, not one call. | "additional 34ms of processing time on a message is so trivial as to be a non-issue, the lag we're trying to not reintroduce is the nightmare thing of 200 queries per minute" — 2026-09-09 20:25. |
| I7 | Constants and prompt strings live outside the mechanism code: user-facing knobs in `tunables.py`, dev-facing constants and prompt strings in their own files, model ids in `model_tier.py`. | "Code should be where mechanisms live, constants should be outside of that" — 2026-08-12 18:36; "the model used specified in model_tier.py, same goes for any future minimodels" — 2026-09-09 16:07; #129. |
| I8 | Journal entries move out of `memories.db` into their own store. Emotion signal entries do not get a store of their own: there is no separate emotions database or emotion-only entries; her felt state (short- and long-term moving averages) is computed from the emotions of surfaced memories plus emotional changes from interactions/events (AMENDED 2026-09-29, emotion-untangle Q6). Exception (AMENDED 2026-10-22): a crash-recovery record of emotion changes may exist only where it is actually needed to recover from a crash; it has no tie to memory or database entries, is never read in normal running, and only a crash-recovery rebuild reads it. | "the emotional signal entries are the ones that get moved to the emotions db" — 2026-09-10 17:18; "the detail about the emotions store being bounded isn't set yet, its pending untangling the mess that is the emotions system in general" — 2026-09-15; #222, #224, #240.; AMENDED 2026-09-29: "as it is now my answer for #6 stands, #222 was from before things got fully untangled, didn't know entirly *what* the damn entries were doing." (Q6: "no seperate emotions database or emotions only entries need exist").; AMENDED 2026-10-22: "The log is purely a crash recovery measure, no tie to memories/database entries, so i'd say its allowed." and "yes in this case; its an only if it can't be avoided sort of thing, don't want a recovery log if that recovery log isn't needed to actually recover from a crash." |
| I9 | Any storage change keeps the legacy import path working and ships a run-once, fail-safe migration that verifies the new stores before removing anything. | "all of these changes need to be done without breaking backwards compatibility … a run-once check … verifying that the updated memory db, emotion db, journal db, etc. are all intact and correct before removing anything" — 2026-09-10 17:01. |
| I10 | Persona-facing and prompt strings carry no LLM tells (no em-dashes) and say "kindled", not "companion"; their wording is the owner's byte-exact call, finalized at the end of a build. | Standing rules the owner set for the project's prompt text. |
| I11 | The live persona is never driven as a test fixture; tests use the synthetic user and persona named in the harness notes. | Standing hard rule the owner set early in the project. |
| I12 | A feature or fix never increases the technical skill required of the user: an optional or heavy component is provisioned/enabled automatically on capability detection, never by a user-run install or a manual pip/python step. Each change should ideally lower the bar, toward a non-technical user eventually running it without issue. | "requiring a user to futz about with python in any way is the exact *wrong* way to do this … a feature addition or bug fix should at minimum not make that worse, and should ideally make things easier on the user, so that eventually a non tech savvy user can use it without issue" — 2026-09-24; F2c LoRA optional-deps. |
| I13 | This is a cross-platform project: every feature, installer, and deployment/provisioning mechanism must work on macOS, Windows, and Linux. Linux/.deb/systemd is one deployment path, not the primary or only one (the user base skews Mac + Windows; Linux is the minority). | "this is a cross platform project; [a collaborator]'s on a Mac, there's one user on windows server … [the owner is] like one of the only users on linux" — 2026-09-24. |
| I14 | Support machinery never outgrows the thing it serves: when a test harness, or a self-calibration (measured costs, fitted bounds), costs more to build than the feature it tests or calibrates, the work stops and the owner chooses keep going, simplify, or freeze. | "if making a test to test something takes longer than making the thing, somethings not right; if the self calibration for a thing takes longer than the thing being calibrated, somethings not right" — 2026-10-10; #321 grew from 55 approved decisions to 247, mostly timing/RAM self-calibration plus a five-times-rebuilt timing harness. |
