# Example design invariants

> This is a real design-invariants doc from one project, scrubbed of names and project details and
> generalised. It is a starter to adapt, not a set of rules to adopt as-is: keep the layout (one checkable
> sentence per row, the owner's words and a date in the second column) and replace the rows with your own.
> Quotes are the owner's own wording with anything identifying cut out; "(paraphrase)" marks a summary.

status: REVIEWED <date>; I4 and I8 amended since     <!-- the owner approved I1 to I11 in chat with corrections to I2, I4 and I8; I12 to I14 were added later, each with the owner's words -->

Standing architectural rules the owner has set. Every sheet, spec, red-team and drift check is checked
against these, row by row. A line is added only with the owner's words and a date; a line is removed only
by the owner. Seeded from quoted rulings in earlier planning transcripts, then reviewed by the owner.

| # | Invariant (one checkable sentence) | Why (owner's words, date, source) |
|---|---|---|
| I1 | There is one store for the records, and data tied to those records (such as association links) lives in it, not in a separate file. | (paraphrase) A separate file for the association links was fragile: after the data was copied between machines, the links had to be reconstructed. <date> |
| I2 | A per-record attribute (an embedding, a cluster tag, the record's own label) is stored on the record row, or in a table keyed by record id; never in a content-addressed side file. | (paraphrase) The per-record embeddings were meant to be an extra column in the main table. <date> |
| I3 | Behaviour thresholds (floors, gaps, cutoffs) are derived or self-calibrating; a hardcoded empirical constant is a tracked defect, never a finished answer. | "magic numbers in code are very rarely the right answer" <date>; the owner also asked whether the floor and gap could recalibrate automatically from the data as it currently stands (paraphrase). |
| I4 | On automatic (passive, per-turn) retrieval, semantic search runs first and ranks first; the keyword, importance, association and recency results are always merged in below the semantic ones, and when the same record is found by both, the semantic result is the one kept. On a search the model initiates, semantic is the default mode and the model can switch it to keyword. | Original: "The semantic search is supposed to be the primary mechanism, the existing lexical is the fallback" <date>; "it runs first on automatic recall" <date>. AMENDED <date>: keyword results always merged in ("Always, merged in"), and "Do it this way: deduping favors the semantic". |
| I5 | A record opened in full gets the full usage-count bump and is enqueued for re-review, whichever path surfaced it. | "Doesn't matter *how* it got surfaced" <date>. |
| I6 | Bulk background work (backfills, sweeps) stays off the response path; a single bounded per-turn step is acceptable; the lag rule targets floods, not one call. | "additional 34ms of processing time on a message is so trivial as to be a non-issue, the lag we're trying to not reintroduce is the nightmare thing of 200 queries per minute" <date>. |
| I7 | Constants and prompt strings live outside the mechanism code: user-facing knobs in one tunables file, developer-facing constants and prompt strings in their own files, model ids in one model-id file. | "Code should be where mechanisms live, constants should be outside of that" <date>; the owner said the same for any future small models (paraphrase). |
| I8 | A running summary of state (a running average, say) is computed from the records it summarises plus the changes from interactions and events; it does not get a store of its own. Exception (AMENDED): a crash-recovery record of those changes may exist only where it is actually needed to recover from a crash; it has no tie to the records or their store, is never read in normal running, and only a crash-recovery rebuild reads it. | Base rule (paraphrase): no separate store and no summary-only entries need exist, once it was clear what those entries were actually doing. <date>. AMENDED <date>: "yes in this case; its an only if it can't be avoided sort of thing, don't want a recovery log if that recovery log isn't needed to actually recover from a crash." |
| I9 | Any storage change keeps the legacy import path working and ships a run-once, fail-safe migration that verifies the new stores before removing anything. | "all of these changes need to be done without breaking backwards compatibility" and a run-once check that the new stores are "intact and correct before removing anything" <date>. |
| I10 | Prompt strings that go into a model's own context carry no LLM writing tells and use the project's agreed vocabulary; their wording is the owner's byte-exact call, finalised at the end of a build. | (paraphrase) A standing rule the owner applies across the project's prompt text. |
| I11 | Real user or production data is never used as a test fixture; tests use the synthetic user and data named in the project's test notes. | (paraphrase) A standing hard rule the owner set early in the project. |
| I12 | A feature or fix never increases the technical skill required of the user: an optional or heavy component is provisioned or enabled automatically on capability detection, never by a user-run install or a manual scripting step. Each change should ideally lower the bar. | "a feature addition or bug fix should at minimum not make that worse, and should ideally make things easier on the user, so that eventually a non tech savvy user can use it without issue" <date>. |
| I13 | Every feature, installer and deployment or provisioning mechanism works on macOS, Windows and Linux; no one platform's deployment path is treated as the primary or only one. | (paraphrase) The user base is mixed across all three platforms, and the platform the developers use is not the typical user's. <date> |
| I14 | Support machinery never outgrows the thing it serves: when a test harness, or a self-calibration (measured costs, fitted bounds), costs more to build than the feature it tests or calibrates, the work stops and the owner chooses keep going, simplify, or freeze. | "if making a test to test something takes longer than making the thing, somethings not right; if the self calibration for a thing takes longer than the thing being calibrated, somethings not right" <date>. The case that prompted it: a fix approved as 55 owner decisions grew to 247 during the build, mostly self-calibration and test machinery. |
